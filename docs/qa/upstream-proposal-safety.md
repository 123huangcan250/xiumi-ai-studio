# Proposal safety on the upstream baseline

Baseline: `f0c819f34ad6c5134065242ddc9b1865212dc830`. This is a narrow compatibility implementation, not a copy of the fork's update-only selection policy. It introduces no inline review UI, multi-selection, typography, image or network feature.

## Contract

- Existing server-owned filter/strict, ignored-operation counts, unique selected subtree IDs, filter removal/anchored insertion and the ban on replacing children remain unchanged. `server/aiEdit.ts` and `src/core/ops.ts` are not modified.
- Acceptance checks the original target against the current document. Changed target leaves reject that item with an explanation, while independent object fields are retained. Arrays, including rich-text content arrays and image collections, are atomic, never positionally merged.
- HTML text changes require the original styled topology and slot-ID set to remain stable, and each targeted text slot to retain its original text. Structure and color/style changes reject. Independent text slots are preserved by revalidating against current HTML. This intentionally does not attempt to merge style changes or changed HTML topology. Upstream replay update rejection remains authoritative.
- Remove/move require the original module to be unchanged and uniquely identifiable. Unanchored numeric insert/move compare against the base replayed through a journal of successfully applied structural operations in actual acceptance order. They reject unrelated top-level ordering changes rather than guessing; explicitly anchored insert continues to follow upstream anchor validation and ordering, including moved anchors, missing anchors and reverse acceptance.
- `resolveProposalItems` is a pure projection shared by preview and acceptance. Preview does not commit history, mark suggestions accepted or mutate the draft. Existing upstream validation regenerates inserted IDs; preview and commit have equivalent content/order, not an identity promise for preview-only generated IDs.
- UI action closures pass the exact proposal identity. A replaced/cleared proposal cannot be resolved by old buttons. Pending status retains repeated-click protection. Undo/redo clear review and never revive it.
- A monotonic in-memory proposal version invalidates in-flight responses after load, clear, replacement, resolve, undo or redo, including undo returning the very same document object. RightPanel still checks the document reference and additionally supplies the captured proposal version. This is not transport cancellation, a multi-selection implementation or a new server authority.

## Verification and boundaries

Tests are real store/core integration with jsdom for HTML parsing, not a claim of strict isolated-unit coverage. One new production module, `src/editor/proposalSafety.ts`, must be included in complete-source coverage measurements. No coverage percentage is claimed here.

The initial new 12-case test file, after correcting a test setup method name, had 10 behavioral failures and two already-passing compatibility cases on the original implementation. These included manual-edit overwrite, stale HTML, old-action identity and undo review lifetime. Two subsequent late-response tests each failed before the corresponding version guard was implemented. Independent review found the initial guard incorrectly rejected the second move in a valid multi-move proposal. Three new real-store/preview tests failed, then passed after recording actual applied structural operations; two further cases preserve external-reorder rejection and mixed insert/remove/move acceptance. Final focused selection/proposal suite: 51 passing tests across four files. Existing upstream anchor/order/policy tests remain unchanged.

Final source gate: full mixed suite 72 files, 751 passing tests and one existing platform skip (752 total); full ESLint, TypeScript and production build passed. The existing build warning about chunks larger than 500 kB remains. Browser interactions have not been newly executed in this cloud environment; upstream Windows CI remains required. No new UI layout, export rendering, snapshot baseline, dependency, package or deployment modification is included.

Four desktop Playwright scenarios were added with a synthetic `page.route` AI provider and real UI actions: stale target title, independent body preservation, accepted-edit undo/redo, and a delayed response after undo/redo returns to the original document. TypeScript, full lint and discovery passed after adding these tests. These four scenarios have **not executed** in this cloud environment; they must pass on Windows before merge. Old rendered-proposal identity is covered by the real-store test; no browser proof of that closure race is claimed. All browser scenarios use the existing isolated E2E server and do not access live model credentials.

Commands ran the installed tools directly via Node (`vitest/vitest.mjs`, TypeScript, ESLint, Vite and Playwright CLI), using dependencies with the same lockfile as this baseline. The cloud pnpm CLI's own dependency status check failed before test execution; no package or lockfile was changed to work around it.
